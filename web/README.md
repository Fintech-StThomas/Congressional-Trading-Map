# Paper Trail (web)

The public site: a board that maps every member of Congress to the organisations and colleagues they are tied to by filed records, with the records one click away. Next.js 16 App Router, TypeScript strict, plain CSS, d3-geo and topojson-client (build time only). No database and no server secrets. The data is not in git: the daily workflow publishes it to Cloudflare R2, and production reads it from there (`DATA_BASE_URL`). Without `DATA_BASE_URL`, pages are prerendered from a local pipeline build in `public/data`, or from the invented fixtures when there is none (see [Run locally](#run-locally) and [Data modes](#data-modes)).

Live: https://red-paper-trail.vercel.app/ · Data contract: [`../docs/data-dictionary.md`](../docs/data-dictionary.md) · Review notes: [`REVIEW.md`](REVIEW.md)

## Data modes

Two server-side environment variables pick where the data comes from. `DATA_BASE_URL` is the base URL under which the generated data tree (`meta.json`, `members.json`, `members/<id>.json`, …) is served, for example `https://pub-xxxx.r2.dev/data`. `RELEASE_BASE_URL` (opt-in, pinned mode) is the base under which immutable releases are archived, for example `https://pub-xxxx.r2.dev/releases` (`<id>/<same tree>`, `<id>/release.json`, and the pointer `current.json`). When both are set, pinned mode wins for every read.

| | `DATA_BASE_URL` unset (local, the default) | `DATA_BASE_URL` set (remote) |
|---|---|---|
| Server reads | `public/data` (or fixtures) with `fs`, at build time only | `fetch(DATA_BASE_URL/<file>)` with Next's fetch cache, `revalidate` 15 minutes (`REVALIDATE_SECONDS` in `lib/data/remote.ts`) |
| Prebuilt at build | every page: 1,569 member pages, 1,569 full files, every state's board strings, every cases page and filter | home, `/wall`, `/cases` (page 1), `/orgs`, `/method`, `/org` shell, `/search-index`; nothing per member |
| Everything else | (all prebuilt) | rendered on first request and cached (ISR), then regenerated at most every hour, so each daily data build reaches the site without a redeploy |
| Browser data | `/data/...` static files from `public/data` | the same `/data/...` URLs, proxied to `DATA_BASE_URL/...` by a `beforeFiles` rewrite (no CORS) |
| `public/data` | read and served | neither read nor served, even if present: `resolve-data` copies nothing and the rewrite runs before `public/` files |

### Pinned mode (`RELEASE_BASE_URL`, opt-in)

Production stays on `DATA_BASE_URL` until the archive publisher is activated; nothing here has been verified against a deployed site (only against a fake bucket, `npm run test:pinned`).

| | Pinned |
|---|---|
| Server reads | `fetch(<base>/<release id>/<file>)` with `cache: "force-cache"` (releases never change). The release is resolved once per render from `<base>/current.json` (`revalidate` as in remote mode, validated strictly by `parsePointer`; an unreachable or malformed pointer is an error, never a guess) |
| Prebuilt / ISR | same routes as remote mode; the live twins serve per-member, per-state and paged routes |
| Browser data | `/releases/<id>/<file>` (a `beforeFiles` rewrite to the bucket, `Cache-Control: immutable`) and the generated JSON at `/r/<id>/board-data/<state>`, `/r/<id>/board-member/<id>`, `/r/<id>/search-index` |
| Release list | `/releases/index.json` (a `beforeFiles` rewrite to the bucket's `index.json`, `Cache-Control: no-cache`: it is mutable and advisory, never used to decide what is current). Read only by `/changes`, which validates it strictly (`validateReleaseIndex`) and shows "comparisons need archived data releases" when it is empty or missing |
| Permalinks | `/r/<id>/m/<member>` and `/r/<id>/m/<member>/records`: one release, a banner, `noindex`, canonical link to the latest page. An unavailable release (never published, withdrawn, malformed id) is a 404 that says so; it is never replaced by the latest data |

How a request stays on one release:

- `lib/data/server.ts`: `latestData()` (React-cached, so layout, page and metadata of one render share one pointer resolution) and `releaseData(id)` (shape checked before any fetch; `null` when its `meta.json` is 404 or outside pinned mode). Both return a `Data` reader (`reader.ts`) whose every accessor reads that one release. Route handlers call `latestData()` once and use only that reader.
- Every page renders `<ReleasePin release={data.release} />`, which sets the browser's release (`lib/data/pin.ts`); `dataUrl()` and `routeDataUrl()` in `lib/urls.ts` then build `/releases/<id>/…` and `/r/<id>/…` URLs, so fetches after render, and after client-side navigation, match the HTML. Server code uses `data.fileUrl()` / `data.routeUrl()`.
- Parsed large files (`orgs.json` is over Next's 2 MB fetch-cache limit) are kept in memory per release, for the 3 most recently used releases (`recent.ts`).
- The footer reads "Latest data as of" on `/r/…` paths (`FooterAsOf`).
- `PT_DIST_DIR` builds into another folder (default `.next`), and `PT_REVALIDATE_SECONDS` shortens the revalidation period; both exist for tests.

### Remote mode

How remote mode is put together (pinned mode reuses the same parts):

- `lib/data/reader.ts` is the only data reader (reached through `latestData()` in `server.ts`); every accessor is async in every mode. In remote mode each read first fetches `meta.json` (small, served from the fetch cache), which gives every route the 15-minute revalidation and an identity (its ETag) for an in-memory cache of the large parsed files (`orgs.json` is over the fetch cache's 2 MB item limit). A 404 for a member's `trades/` or `holdings/` file means "none", as locally. Any other failure throws: at build time the build fails with the URL in the message; at request time the page shows the error page (`app/error.tsx`, HTTP 500, not cached) and the layout falls back to "Data as of unknown" rather than failing.
- Route segment config (`dynamicParams`) must be a literal, so the per-member, per-state and paged routes have twins under `app/live/` with `dynamicParams = true` and no static params. In remote mode `next.config.ts` rewrites `/m/:id`, `/m/:id/records`, `/board-data/:state`, `/board-member/:id` and `/cases/:slug+` to them (`beforeFiles`); URLs do not change. The feed (`/feed/m/<id>.xml`) and embed (`/embed/m/<id>`, with `?theme=dark` rewritten to `/embed/m/<id>/dark` in every mode) routes follow the same twin pattern; the site feed `/feed/trades.xml` is one static route (`revalidate` 3600) in every mode, reading at most 60 member trade files. In local mode the twins are never linked and answer 404, and the original routes are unchanged (`dynamicParams = false`, everything prerendered).
- Values computed from the data at build time: the data's current year (`NEXT_PUBLIC_YEAR_MAX`, from `wall-years.json`) is fetched by `next.config.ts` during the build, and a failed fetch fails the build; it is baked in until the next deploy (it changes once a year). The search index (`/search-index`) and the featured example (home page) are computed from fetched data at build and recomputed on revalidation. State outlines (`lib/board/geo.ts`) use a static import of the versioned `public/geo/us-states.json`, compiled into the server bundle. Build-time and ISR renders therefore use the same geometry without reading the deployed filesystem or fetching a CDN.

To try remote mode locally, point `DATA_BASE_URL` at the public bucket (https://pub-b6acb08f97e345d68ebc4629e915f8ab.r2.dev/data), or serve a copy of a data tree under `/data` with any static server that returns 404 for missing files (`DATA_BASE_URL=http://localhost:3200/data`).

## How data is resolved (local mode)

`scripts/resolve-data.mjs` (run before `dev` and `build`) and `src/lib/data/source.ts` (used by `next.config.ts` and the server code) apply one rule:

| `PT_DATA` | Uses |
|---|---|
| `fixtures` | fixtures, always |
| `real` | `public/data` whenever `members.json` exists |
| unset | `public/data` when its `meta.json` has `publication_budget` (a current-contract build), else fixtures |

On fixtures the files are copied to `public/sample-data/` (gitignored) and every page carries a SAMPLE DATA stamp. On Vercel or CI (`VERCEL` or `CI` set) that fallback is refused: with neither `DATA_BASE_URL` nor a real `public/data` build, `resolve-data` and `next.config.ts` (`sampleFallbackError` in `source.ts`) fail the build with a message, unless `PT_DATA=fixtures` asks for the sample site explicitly. The browser reads the base path from `NEXT_PUBLIC_DATA_BASE` and the data's current year from `NEXT_PUBLIC_YEAR_MAX` (both set in `next.config.ts`).

- **Build time (server)**: `lib/data/server.ts` reads `members.json`, member files, `cases.json`, `meta.json` and so on with `fs`. Nothing reads data at request time, and `outputFileTracingExcludes` keeps the JSON out of server bundles.
- **Build-time JSON routes**: `/board-data/<STATE>` (each current member's board strings and node names), `/board-member/<id>` (former members), `/search-index` (members and the 6,000 largest organisations, so `orgs.json` never ships).
- **Browser**: `lib/data/fetch.ts` `getJSON` fetches each URL once per page load and rejects on non-2xx; `decode.ts` turns columnar tables (trades, ledger, org ties) into objects. Organisation pages load `orgs/<sha1(id)[0:2]>.json`; a tie with an `edge` id loads that member's file for its evidence.
- **Contract rules the UI keeps**: amounts are ranges (`amountText`, never a midpoint); missing is never zero; owner is shown as filed; `ledger_totals` covers ties that are *not* listed, so totals are listed + ledger (`orgTieTotal`).

## Run, test, screenshot

```bash
cd web
npm install
npm run dev                         # http://localhost:3000
npm run build                       # prebuild picks the dataset; postbuild runs eslint
npx next start -p 3100
npm test                            # unit tests + Playwright smoke tests (starts its own server on :3123 unless BASE_URL is set)
BASE_URL=http://localhost:3100 npm test
node --test tests/logic.test.mjs    # one unit file, no server
npm run test:pinned                 # opt-in: builds the site against a fake release bucket (PT_DIST_DIR=.next-pinned, removed afterwards) and drives Chromium
```

Tests use the lockfile-pinned `playwright` package, not `@playwright/test`. Install its Chromium browser with
`npx playwright install chromium` (CI also uses `--with-deps`). `npm run test:unit` excludes browser and deployment suites.

`tests/geo-deployment.test.mjs` runs with the fixture build in `npm test` (including CI). It copies the compiled site into an isolated directory with no `public/geo` or `.cache`, supplies only the fixture dataset, and forces two on-demand homepage regenerations. Each must report `REVALIDATED` and render all 51 state/DC paths, nation and borders. The original build and source assets are untouched. Remote and real-data builds skip this isolated fixture test.

What the tests run against: the unit tests need no data (they use inline data and `fixtures/`). The smoke tests run against whatever the build used and check, at start, whether the site serves a real `/data/meta.json`. In a clean checkout (no `public/data`, no `DATA_BASE_URL`) the build is the sample site: the smoke tests that work on the fixtures run, and the 14 that need real members and files (K000389's full file, the wall, organisations, cases pages) are skipped with "needs real data". To run them all without the pipeline, build and start with `DATA_BASE_URL` (way 2 above). `tests/wallyears.test.mjs`'s real-data check reads `DATA_BASE_URL` when set, else `public/data`, else is skipped with the same message.

## Deploy on Vercel

Create a project with **Root Directory `web`**, framework Next.js, default build command (`npm run build`). Set `PT_DATA=fixtures` only to build the sample site on purpose. Data files are excluded from server bundles in both modes.

**Remote mode (production):** in the Vercel project, Settings → Environment Variables:

| Name | Value | Environments |
|---|---|---|
| `DATA_BASE_URL` | `https://pub-b6acb08f97e345d68ebc4629e915f8ab.r2.dev/data` (the public base URL of the data tree; no trailing slash needed; the bucket must serve `meta.json`, `members.json`, … directly under it and return 404 for missing files) | Production and Preview |

It is read at build time: the rewrites, the data year, which routes prebuild and the URL the server functions fetch from are all fixed by the build (`next.config.ts` inlines it for the server code), so changing it needs a redeploy, and Preview builds need it as much as Production. Nothing else is needed: no CORS rules (the browser only talks to the site), no secrets (the bucket is public). In remote mode nothing reads `public/data` (it is not in the repository anyway), so the build only prerenders the handful of routes listed above.

If `DATA_BASE_URL` is missing on Vercel, the build fails with "refusing to build the SAMPLE site" instead of publishing the fixtures (set `PT_DATA=fixtures` to build the sample site on purpose, e.g. for a demo). If it is set but unreachable or malformed at build time, the build fails with the URL in the error. If storage is down at request time, pages already generated keep being served (stale) and first-time pages show the error page until it is back. Geometry: `public/geo/us-states.json` (us-atlas states-10m) is a required static import. A missing asset fails compilation; incomplete/invalid projected geometry fails prerendering rather than publishing an empty map. No CDN/cache fallback is used.

**Pinned mode (opt-in):** set `RELEASE_BASE_URL` (Production and Preview, build time, like `DATA_BASE_URL`) to the public base of the `releases/` prefix. Production stays on `DATA_BASE_URL` until the archive publisher is active and the cutover is decided; do not set both on production without meaning to switch (pinned wins). The bucket must serve `current.json` and `<id>/…` and return 404 for missing files. Not verified on a deployment.

## Positions and financial history

and show that timelines are unavailable until a new pipeline build is published.
